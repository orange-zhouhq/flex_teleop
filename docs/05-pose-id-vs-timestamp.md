# 05 · 为什么用 pose_id 而不是时间戳

## 一句话

**时间戳描述"何时"，`pose_id` 描述"哪一个"。**

插值需要的是"哪两个端点 + 比例"，溯源需要的是"这一拍属于哪一帧"，丢帧判定需要的是"少了第几帧"——**这些问题的答案都是"哪一个"，不是"何时"**。

---

## 1. 两者的语义边界

| | 时间戳 `stamp` | `pose_id` |
|---|---|---|
| 本质 | 一个实数（物理时刻） | 一个整数（身份） |
| 单调性 | 依赖时钟质量，可能回跳 | 由算法保证，严格递增 |
| 跨设备可比 | 需要同步（PTP / chrony） | 不需要（同一分配器产出） |
| 精度 | 受时钟与打点位置影响 | 精确（无量化误差） |
| 可重建 | 依赖当时的时钟状态 | 永久有效 |

一个关键事实：**`pose_id` 是"分配"出来的，时间戳是"测量"出来的**。分配的值不可能有歧义，测量的值总有误差。

---

## 2. 八个维度的对比

| 维度 | 时间戳方案 | pose_id 方案 | 胜出 |
|---|---|---|---|
| **α 计算** | `(t_exec − stamp_a) / (stamp_b − stamp_a)` | `(t_exec − t_a) / (t_b − t_a)`，t 为本地到达时刻 | 平手* |
| **乱序 / 重复丢弃** | 比较 stamp；相等、回跳时无判据 | `id ≤ max_seen` → 丢弃，O(1) | **id** |
| **丢帧检测** | 间隔 > 1.5×周期 → 疑似，有误判 | `id_new − id_old > 1` → 精确数量 | **id** |
| **保活语义** | 需额外约定"定期发帧" | id 递增即保活，停滞即断链 | **id** |
| **因果溯源** | 需保留时间窗口，离线查询 | 每拍显式携带 `(id_a, id_b, α)` | **id** |
| **多传感器对齐** | 需与所有传感器时钟同步 | 传感器打标时查插值器，零同步 | **id** |
| **离线回放** | 按时间重放，依赖时钟一致性 | 按 id 重放，确定性 | **id** |
| **延迟测量** | 直接可得 | 需结合本地时间与 ack | **stamp** |

\* α 本身两套方案都能算。`pose_id` 的胜出不在这里，而在它携带的**身份语义**。

---

## 3. 三个真实失效场景

### 3.1 NTP 校时导致乱序误判

**场景**：VR 主机与机器人各自接入 NTP。某次校时，VR 侧时钟回跳 200ms。

**时间戳方案**：
```
stamp 序列：... 1000.00, 1000.033, 1000.067, 1000.200(★跳回), 999.900, 999.933 ...
```
接收侧判定 `999.900 < 1000.200` → 判为乱序 → **丢弃后续 5 帧** → 插值器 HOLD 约 200ms → 操作者手感"顿一下"。

**pose_id 方案**：
```
pose_id 序列：... 101, 102, 103, 104, 105, 106 ...
```
时钟回跳对 id 没有影响。帧照常接收、照常插值。stamp 只在诊断日志里记一笔。

### 3.2 相机与 VR 无同步

**场景**：想为每帧图像标注"此刻的机器人目标位姿"，用于模仿学习数据集。相机在另一台机器上，与 VR 端没有共同时钟。

**时间戳方案**：
- 需要把相机与 VR 端做时间同步（PTP 或软件同步）
- 典型同步误差 10–50ms
- 30Hz 下 33ms 就是一整帧的错位
- 数据集里"图像—动作"配对存在系统性偏差，训练时会学成"动作滞后于视觉"

**pose_id 方案**：
- 图像到达的瞬间，查一下插值器当前状态 → 得到 `(id_a, id_b, α)`
- 这个三元组直接附着到样本上
- **零同步成本**，误差只来自相机自身的曝光延迟（可标定扣除）

```json
{ "image": "k.png", "src": {"id_a": 100, "id_b": 101, "alpha": 0.62},
  "q_fb": [...], "T_actual": [...] }
```

这条样本在任何时候、任何机器上回放，都能精确重建当时的目标位姿。

### 3.3 丢帧归因

**场景**：端到端延迟突然从 60ms 涨到 150ms，需要定位是网络丢帧、上游卡顿，还是下游求解变慢。

**时间戳方案**：
- 只能看到"这一帧的 stamp 比预期晚了 90ms"
- 无法区分"上游 30Hz 变慢了"和"网络丢了一帧又来了新帧"

**pose_id 方案**：
- `id_new − id_old = 4` → 明确知道中间丢了 3 帧
- 丢帧发生在**哪一段**也能查：接收侧记录"收到 id=105 时 id=101 之后没见过"
- 与求解耗时 `solve_us` 对照，直接区分网络问题与算力问题

---

## 4. 时间戳不可替代的地方

**延迟测量。** `pose_id` 没有时间语义，它永远回答不了"慢了多久"。

所以最终形态是三者并存，各管一段：

| 机制 | 唯一职责 |
|---|---|
| `pose_id` | 帧身份、乱序丢弃、丢帧计数、因果分组、多传感器打标 |
| `tick_seq` | 同一拍上"指令 ↔ 反馈"的配对 |
| `stamp` | 端到端延迟、抖动统计、录制回放的时间轴 |

**任何一方越界都会出错**（见 [02-frame-alignment.md](02-frame-alignment.md)「三个 ID 的职责边界」）。

---

## 5. 采用 pose_id 的真实成本

不掩饰：这不是零成本方案。

| 成本项 | 说明 |
|---|---|
| **消息字段** | 每个跨进程消息要加 `uint64 pose_id`。ROS 2 没有内置 seq，必须显式加 |
| **源头约束** | 分配侧必须"无条件递增"，手不动也要发帧。这条不进协议就等于没做 |
| **全链透传纪律** | 任何环节不得重生 id。一旦有人"为了方便"重新编号，整条链的溯源就断了 |
| **调试习惯** | 日志里要打 id，不能只打时间戳 |

对应的收益：丢帧可计数、乱序无歧义、多传感器零同步对齐、数据集可精确重建。

---

## 6. 为什么工业界仍常用时间戳

诚实地说，时间戳有它的合理性：

- **零协议改动**：ROS 2 消息天生带 `stamp`，不用改定义
- **标准工具链**：`message_filters::ApproximateTime` 开箱即用
- **单机场景够用**：同一时钟域、无跨机传输时，时间戳不会出问题
- **人眼友好**：日志里的时间戳比 id 直观

**这些便利在下面这些条件下会失效**：跨机器、多传感器、需要离线重建、需要丢帧计数、需要数据集对齐。

`flex_teleop` 面向的正是这些条件。

---

## 7. 一句话总结

> 时间戳方案在"时间轴"上对齐，`pose_id` 方案在"身份轴"上对齐。
>
> 时间轴会被时钟、网络、抖动污染；身份轴只有一条规则——**单调递增，全链只读**。
>
> 用时间轴做延迟测量，用身份轴做其余一切。
