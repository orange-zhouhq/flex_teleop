## 1:N 外键，不是合并 ID

30Hz : 200Hz = **3 : 20**。一个 pose 帧对应 6~7 个 tick，逐帧在 6/7 之间循环。

```
pose_id 100 ─┬─ tick 1000   (id_a=100, id_b=101, α=0.00)
             ├─ tick 1001   (id_a=100, id_b=101, α=0.15)
             ├─ tick 1002   (id_a=100, id_b=101, α=0.30)
             │   ...
pose_id 101 ─┼─ tick 1007   (id_a=100, id_b=101, α=0.90)
             ├─ tick 1008   (id_a=101, id_b=102, α=0.05)
```

注意 α 的锯齿：`0 → .15 → .30 → .45 → .60 → .75 → .90 → .05 → .20 …`，每 3 帧（40 个 tick）循环一次，**永远不会均匀走满 0→1**。

推论：
- 不能用"α 单调推进"做健康判据
- 任何对 α 做数字滤波的实现都会变成周期性时变系统

查询：`WHERE id_a <= P < id_b` 取出该 pose 帧影响过的全部关节指令。

## 三个 ID 的职责边界

| 机制 | 分配点 · 频率 | 能做什么 | **不能做什么** |
|---|---|---|---|
| `pose_id` | 采集侧 · 30Hz | 帧身份 / 乱序丢弃 / 丢帧判定 / 因果分组 | 测延迟——没有时间语义 |
| `tick_seq` | 机器人侧 · 200Hz | 指令↔反馈同拍配对 / tick 级丢包 | 跨机对齐——两机基数不同 |
| `stamp` | 各端本地 | 端到端延迟 / 录制回放 / 抖动统计 | 帧身份——跨机不同源、可跳变 |

**同一个问题，三种查询各用各的键：**

| 问题 | 用哪个 | 形式 |
|---|---|---|
| 这帧 VR 目标影响了哪些关节指令 | `pose_id` | `ticks WHERE id_a <= P < id_b` |
| 这一拍的反馈配哪条指令 | `tick_seq` | `q_cmd.tick_seq == q_fb.tick_seq` |
| 端到端慢了多少 | `stamp` | `t_now − t_stamp(pose_id_ack)`（需时钟同步） |

## 契约约束

这三条不写进协议，前面的对齐全是假的：

1. **保活帧**：`pose_id` 按标称频率无条件递增。手不动也出帧、id 照涨。否则"id 停滞"分不清静止还是断链，所有超时判据失效。
2. **HOLD 冻结溯源标签**：解不出来时 `q_cmd` 保持上一帧，`(id_a, id_b, α)` 也冻结在最后成功那帧。否则会谎报"这拍在追新目标"。
3. **ack 语义**：`pose_id_ack` 表示"该 id 的影响已全部下发"，**不等于"已执行到位"**。做超时保护够用，做精度评估不够。

## 视觉 / 传感器的帧对齐

图像不需要带 id，也不需要与 VR 端时钟同步：

```
相机 15/30/60Hz ──▶ 图像 k ──▶ 打标 ──▶ 样本
                                  ↑
遥操目标 ─────────────────▶ (id_a, id_b, α)
```

图像到达时刻查询插值器状态，得到 `(id_a, id_b, α)` 并附着：

```
{ image_k, (id_a, id_b, alpha), q_fb, T_actual }
```

- 零额外同步成本——插值器状态本来就在内存里
- 帧率不同也能落进同一套区间（15Hz 会跨区间，60Hz 两帧共享区间）
- 多相机、多传感器共用一套对齐口径

**落地注意**：若相机链路有固定延迟（USB 传输、编码），打标时刻晚于真实曝光时刻，α 会整体偏移。应在取区间前扣除标定延迟。
